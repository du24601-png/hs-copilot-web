# 查询后台架构梳理与测试问题分析（2026-09-03）

## 一、整体查询链路（现在实际在跑的流程）

一次完整查询分两步走，全部由 `server.js` 承担（零依赖 Node 原生服务）：

**第一步：POST /api/classify —— 准备确认页**

1. 用户提交大白话商品描述（最多 200 字）。
2. **双路并行检索候选编码**（都只查本地 SQLite 税则库）：
   - **字面检索**：把描述切成中文片段做 n-gram 匹配品名，最后一个词的末字/末两字当"中心词"大幅加权（比如"触控笔"的"笔"），另查 CIQ 俗名表（口语名→编码映射）。
   - **LLM 规划检索**：让大模型把描述拆成四层（核心商品/结构/材质/参数），并给出税则同义词（保温杯→保温瓶）和可能章节号，按这些词再去库里查。
3. 两路结果**加权合并**（规划词权重高于字面词），按品目（前 4 位）分家族，共选 16 个候选，每个品目家族最多占 6 席。
4. 大模型 P1 阶段：拿着真实候选列表，抽出已知属性、生成 0-3 个关键确认问题。结果缓存 24 小时。

**第二步：POST /api/decide —— 出最终结论**

1. 带上用户在确认页的答案；自由补充文本先做清洗（用户嘴上说的 HS 编码会被剔除，防止反向污染）。
2. 用"描述+补充"重新走一遍上面的候选检索。
3. 大模型 P2 阶段：从候选中选最终 10 位编码，给理由、反事实提示、备选。
4. **校验兜底**：结论编码必须能在候选列表里找到，选不出来就拒答；税率、申报要素等一切数字只从数据库取，不信模型的输出。

另有 /api/search（搜索联想）和 /api/hs/:code（编码详情）两个直查库的接口。

一句话概括设计原则：**数据库管"事实"，大模型管"理解"，模型无权编造任何编码或税率。**

## 二、本次测试结果

**单元测试**：26/26 全部通过（需用 Node 24 运行，见问题 ④）。

**真实商品 20 例端到端测试**（只给描述、跳过确认问题、空答案直接 decide）：

- 正确：**2/20（10%）**（real-007 脱水苹果粒、real-016 迷你全地形车）
- 错误编码：8 条；拒答：10 条
- 平均耗时 5.5 秒，接口零故障
- 比上次记录的 3/20（15%）更差——本身波动就是问题之一（见问题 ③）

## 三、问题定位与根因

### 问题 ① 检索层召回天花板：正确编码只有 7/20 进入候选池

这是最大瓶颈。候选池进不去，后面全白搭——10 条拒答的直接原因都是"正确税号不在候选里"，P2 的拒答其实是**校验机制在正确地兜底**，错在检索层。

具体根因（都已逐条复现验证）：

1. **口语词与税则词完全脱节**。全库品名里"淋浴房"出现 0 次（税则叫"钢铁制门窗及其框架"）、"血糖试纸""醋精""氧化锆块"同理。字面检索对这些词天然失明，只能指望 LLM 规划的兜底，而兜底本身有三个机械缺陷（见下）。
2. **单位词污染**。"20 亿每毫升"的"毫升"恰好命中 8703 品目下大量车辆编码（品名带"…不超过 1000 毫升"），加上"以词结尾加分"规则，把一整个车辆家族顶进了候选池，挤掉了真正的目标。real-002（微生物肥料）、real-009（食用醋精）的候选前几名全是越野车，就是这个原因。
3. **兜底检索"命中即停"造成漏检**。规划层取后缀词时，从最长试到最短、一旦命中就停：淋浴房描述里的"带金属框架"→先试 4 字后缀"金属框架"，命中了 9401 坐具（3 条）就停止，2 字的"框架"（能命中 7308300000 钢铁制门窗框架）永远轮不到。
4. **章节兜底拿整句话当关键词查**。codesInChapter 把"固定玻璃和滑动玻璃组合，带金属框架、滑轮"这种长句整串做 LIKE 查询，必然 0 命中，等于章节信号被浪费。
5. **"其他 XX"兜底税号被系统性挤出**。品目内 6 席上限 + 按码序位置衰减，导致每个家族排在编码序列末尾的"其他肥料(3105909000)""其他玻璃制品(7020009990)"这类兜底码永远垫底被裁。而海关裁定恰恰爱把疑难商品归进兜底码——本题库里 20 个标准答案有一大批以 90/99 结尾。

### 问题 ② 决策层换手率低：正确码在池中的 7 例，只选对 2 例

检索层给了正确答案，P2 依然选错或拒答（real-001/004/014/019/020）：

- **10 位细分需要裁定口径知识，模型没有**。碎干辣椒"切成圈丝丁、未磨成粉"，模型按品名字面选了"未磨碎"0904.21，但官方裁定切碎即归 0904.22；块状马苏里拉该归"未熟化鲜乳酪"0406.10，模型选了"其他"0406.90；吻合器该归 9018909911，模型选了同品目的 9018908000。这些区分点在品名和注释里并无明示，靠的是归类总规则和裁定先例——P2 只拿到候选的名称/注释/申报要素，缺这块知识注入。
- **该认领的时候不敢认领**。real-019 一轮运行里 7308300000 明明在候选池中，P2 仍以"候选都是门窗坐具"为由拒答——模型没把"不锈钢框架淋浴房"和"钢铁制门窗及其框架"对应起来。拒答方向没错，但说明候选里有效项被淹没在无关项中时，模型识别不出来。

### 问题 ③ 结果不可复现：同样的描述，两轮测试结果不同

- 未设置 temperature 等采样参数，两次运行候选池和结论都会漂移：real-019 一轮进池、一轮没进；real-020 上轮对、本轮错；real-013 上轮拒答、本轮给了错误编码。
- classifyCache（24 小时）会把一次结果"冻住"，掩盖了不稳定性；服务重启后结果就变。这对调试和回归测试都是干扰：**不先固定随机性，任何优化的效果都测不准**。

### 问题 ④（工程小问题）：npm test 在默认 Node 22 下跑不起来

`--test-isolation=none` 参数只有 Node 24 认；Node 22 里叫 `--experimental-test-isolation`。用系统 Node 24 跑即可全绿，或改 package.json 兼容两者。

## 四、改进优先级建议（按性价比排序）

1. **固定随机性**（几行改动）：LLM 请求加 `temperature: 0`（或 0.1），让测试可复现。这是做后续一切优化的前提。
2. **检索清洗与兜底修补**（纯代码，不花钱）：
   - 单位/量词停用词表（毫升、公斤、厘米、伏特…），不让它们参与打分；
   - 后缀匹配"命中即停"改为继续尝试更短后缀、按命中数择优；
   - codesInChapter 对长句先分词再逐词查，不整串 LIKE；
   - 给"其他 XX"兜底税号设保护席（每品目家族保留 1 席），或降低码序位置衰减的影响。
3. **决策层知识注入**：把品目注释、子目规则要点随候选一起喂给 P2；必要时维护一个小的"裁定口径知识表"（切碎=粉碎等），比换更大的模型便宜。
4. 修 npm test 的 Node 22 兼容性。
