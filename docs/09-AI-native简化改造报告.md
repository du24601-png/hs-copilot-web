# AI-native 简化改造报告（2026-09-03，第三轮后台改造）

> 目标：不再给旧检索算法堆权重和规则，验证一条更简洁的链路是否更优：
> **用户描述 → LLM 商品理解/查询规划 → SQLite 宽松召回 → LLM 候选比较与追问 → SQLite 最终核验**
>
> 回滚点：git tag `backup-before-ai-native`（commit e4367d5），数据库与前端（index.html / app.js / styles.css / confirm-logic.js）未做任何修改。

## 一、新后台完整流程图

```
用户描述（≤200字，不可信输入）
        │
        ▼
┌─────────────────────────────────────────────┐
│ LLM① 商品理解 + 查询计划   temperature = 0   │
│ 只做两件事，输出固定 JSON：                  │
│   core_product / function / materials /      │
│   structure / usage / specifications(规格)   │
│   search_terms / hs_synonyms /               │
│   possible_headings(4位品目, ≤5, 宁多勿漏)   │
└─────────────────────────────────────────────┘
        │ 失败 → fallbackProfile（仅原文关键词，degraded 透传前端）
        ▼
┌─────────────────────────────────────────────┐
│ SQLite 宽召回 broadRecall（目标：不漏正确码）│
│ 三路 UNION：                                │
│  ① LLM search_terms / hs_synonyms → 品名LIKE │
│  ② 原文基础关键词：stripSpecs 后 n-gram(4→2) │
│     无命中即停；同片段长词覆盖短词不去重计分  │
│  ③ CIQ 俗名表（口语名→编码，+2 分）          │
│ 计分仅两条：品名命中按 IDF 极简档 +2/+1/+0.3 │
│ 规格单位(ml/kg/cm/V/W/%/数字)只进画像，      │
│ 一律不参与召回匹配                           │
│                                             │
│ possible_headings = 信号，不是门槛：         │
│  · 建议品目整品目展开（≤12条/品目，          │
│    命中分行优先，“其他”兜底码其次）          │
│  · 关键词可从任何其他品目找回候选            │
│  · 裁池：按分取前30 + 每建议品目软保底3席    │
│    （top-2 命中行 + 首个“其他”兜底码）       │
│ → 候选池约 30~40 条真实编码                  │
└─────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────┐
│ LLM② 候选比较          temperature = 0       │
│ 输入：商品画像 + 候选池（品名/章/注释/要素） │
│ 输出固定 JSON：plausible_candidates /        │
│   key_differences / missing_critical_        │
│   information / need_clarification /         │
│   clarification_question（至多 1 个问题）    │
│ 不要求立即给最终编码                         │
└─────────────────────────────────────────────┘
        │ 会话按 query 缓存：画像+候选池+比较结论（24h）
        ▼
   用户回答确认问题（benchmark 为空答案）
        │
        ▼
┌─────────────────────────────────────────────┐
│ decide：不从头检索                          │
│  · 答案并入画像 confirmed 字段               │
│  · 自由文本先剥离用户声称的 HS 编码（防污染）│
│  · 用【原候选池】交给 LLM③ 终选 t=0          │
│  · 仅当 LLM③ 判定 product_nature_changed     │
│    且答案确有新信息 → 重新理解+召回，每轮≤1次│
└─────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────┐
│ SQLite 最终核验（模型无权编造任何事实）      │
│  · selectedCode 必须 ∈ 候选池，否则拒答      │
│  · 编码名称/税率/监管条件/申报要素           │
│    全部重新从 SQLite 按编码取                │
└─────────────────────────────────────────────┘
        ▼
   最终结论（hs 字段为数据库权威数据）
```

## 二、实际删掉的旧逻辑

| 删除项 | 旧实现位置 | 替代方式 |
|---|---|---|
| 末字/末两字中心词特殊加权（useHeadBoost，5×/10× 权重） | retrieveCandidates | 删除。LLM① 的 core_product 直接给出核心词 |
| 后缀“命中即停”（suffixOnly 从最长试到命中就 break） | retrieveCandidates 后缀分支 | 删除。n-gram 所有长度命中都保留 |
| 码序位置衰减（index×0.02 递减） | mergeCandidateCodes.bump | 删除。宽召回不按位次扣分 |
| 每 Heading 固定 6 席硬裁剪 | pickRetrievalGroups / pickDiverseCodes | 删除。改为每建议品目 3 席软保底（含兜底码保护） |
| 长句直接 LIKE（codesInChapter 整句查库） | codesInChapter | 删除。品目改为整品目展开，不做文本匹配 |
| 四层规划分层加权合并（PLAN_WEIGHT base/core/alt/chapter/structure/material/param 七档权重） | mergeCandidateCodes | 删除。三路 UNION + 单一 IDF 档 |
| 品名结尾加分（posBonus endsWith ×2） | retrieveCandidates.addRows | 删除 |
| P1 生成 0-3 个确认问题 | P1_SYSTEM | LLM② 至多 1 个“最能改变判断”的问题 |
| decide 重新全文检索 | apiDecide | 会话复用原候选池，仅商品本质改变才重检索 |

保留：CIQ 俗名表、基础关键词匹配（n-gram）、LLM search_terms/税则同义词、possible_headings、编码防注入清洗、结论数据库核验。

## 四、20 例基准对比

同一测试集 `test/fixtures/real-products-noisy-20.json`，同一方法（classify → 忽略追问 → 空答案 decide → 精确匹配）：

| Metric | 旧版 | 新简化版 |
|---|---:|---:|
| Heading Recall | 12/20 | **19/20** |
| HS10 Candidate Recall | 7/20 | **12/20** |
| Final Correct | 2/20 | **5/20**（三次完整跑分 8 / 6 / 5，区间 5~8/20） |
| Refusal | 10/20 | **0/20** |
| Avg latency | 5.5s | 14.9s（实测区间 14~27s，受供应商波动影响） |
| 平均候选数 | 16（设计上限） | **34.1** |
| 平均 LLM 调用次数 | 3（plan+P1+P2，decide 复用 plan 缓存） | **3**（理解+比较+终选） |

结果文件：`tools/real-products-20-simplified.json`（最终代码、清缓存、全新进程实测）。

解读：
- **召回是决定性改善**：正确品目进池率 60%→95%，正确 10 位码进池率 35%→60%，拒答从 10 降到 0。旧版 10 条拒答全部是“正确码不在池里”，本轮全部解决。
- **最终正确率提升到 2.5~4 倍但跑分间有波动**（5~8/20）：波动不在召回侧（三轮 Heading/HS10 召回几乎一致），而在 LLM③ 终选对临界案例的选择（见失败分类 C 类）。temperature=0 下 DeepSeek 仍存在服务端非确定性。
- **延迟上升是唯一回退项**：3 次串行 LLM 调用 + 30~40 条候选的大 prompt。旧版 plan 与字面检索并行、候选只有 16 条。

## 五、20 例失败阶段分类（最终跑分，失败 15 例）

| 阶段 | 数量 | 案例 | 机理 |
|---|---:|---|---|
| A. LLM① 品目信号缺失（正确品目完全未进池） | 1 | real-009 醋精（只建议 2209，未给 2106） | 总酸 20%+调味物的裁定口径超出“食醋”直觉，LLM① 没想到兜底食品品目 |
| B. 品目在池但正确 10 位码未进池 | 7 | real-003/011（3824 共 41 行超展开上限）、015（8481 26 行）、016（8703 295 行）、017（3822 关键词分占满保底席）、018（7020 仅靠关键词命中部分行）、020（9018 42 行） | 大品目展开上限 12 条 + 零命中的兜底码在裁池中仍可能被挤掉 |
| C. 正确码已在池，LLM③ 终选选错 | 7 | real-001（090422 切碎=已磨）、005（8517799000→…500）、008（2005519900→0713）、010（6914900000→6914100000）、012（8543709990→8541511900）、013（8711600000→8712004900）、019（7308300000→7308900000） | 10 位细分依赖裁定口径知识（切碎即磨、预烧即陶瓷、结构排除条款），模型只有品名/注释/申报要素 |
| 拒答 | 0 | — | 旧版 10 条拒答全部消除 |

**瓶颈已从检索层转移到决策层**：60% 的案例正确编码已在候选池中，但终选只对 1/3。下一轮性价比最高的是给 LLM③ 注入裁定口径知识（归类总规则六条、本国子目注释、归类决定/常见裁定模式如“切碎=粉碎”），而不是继续改检索。注意：这三类知识库内均无（`hs_code.note` 实为税则备注栏而非品目注释），需从官方《进出口税则》正本及海关总署公告补录。

## 六、三个案例完整 debug

完整追踪文件在 `tools/debug/*.json`（每案例 3 轮）。

### 案例 1：全不锈钢框架弧形玻璃淋浴房（real-019，期望 7308300000）

- **LLM①**：core_product=玻璃淋浴房；search_terms=[淋浴房,玻璃隔断,弧形玻璃,不锈钢框架]；hs_synonyms=[淋浴房,玻璃隔间,金属框架玻璃结构体]；possible_headings=[9403,7308,7008,7020]（逐轮略有变化）
- **宽召回**：池 37~43 条；`淋浴房` 全库 0 命中（与旧版一致），但 **7308 整品目展开 5 条全部进池**，7308300000 三轮均在池 ✅（旧版它多次被 6 席硬裁剪+码序衰减挤出）
- **LLM②**：plausible 稳定包含 7308 家族；追问质量很高：“该淋浴房是永久性建筑结构安装，还是独立可移动家具？”——正是 7308/9403 的分界
- **LLM③**：三轮选中 7308900000（其他钢铁结构体）×3，benchmark 跑分另选中过 7308300000✓ 与 9406900090✗
- **结论**：召回问题已修复；剩余错误是终选未用上“门窗及其框架” vs “其他结构体”的细分口径。真实交互中 LLM② 的追问大概率能把它拉回 7308300000

### 案例 2：复合微生物肥料液 20亿/毫升（real-002，期望 3105909000）

- **LLM①**：specifications 正确收编“有效活菌不少于20亿每毫升、总养分16%到18%”；possible_headings=[3101,3105,3808]
- **宽召回**：池 36 条；`毫升` 被剥离后 8703 车辆家族零污染（旧版头几名全是越野车）；**3105909000 经“每品目首个‘其他’兜底码保底席”进池** ✅（旧版它因 6 席上限+码序垫底被裁）
- **LLM②**：plausible[0]=3105909000（三轮一致）；追问“是否作为肥料产品销售、是否经化学处理”——正是 3101/3105 分界
- **LLM③**：三轮稳定选中 **3105909000 ✓✓✓**
- **结论**：旧版两个致命伤（单位污染、兜底码被裁）均被结构性消除

### 案例 3：不锈钢保温杯 500ml（临时用例，不在 20 例真值集内）

- **LLM①**：core_product=保温杯；hs_synonyms=[保温瓶,真空容器,不锈钢容器]；specifications=[500ml]；possible_headings=[9617,7323]
- **宽召回**：池 34 条；`保温杯` 全库 0 命中，同义词 `保温瓶` 命中 9617 家族（9617001100/1900/9000）+ `500ml` 完全未参与匹配
- **LLM②**：plausible=[9617001900, 9617009000, 7323930000, …]；追问“内胆材质是什么”（区分 9617001100 玻璃内胆 vs 9617001900）
- **LLM③**：三轮稳定选中 **9617001900（其他保温瓶）**，理由正确引用“不锈钢非玻璃内胆、成品非零件”——这正是保温杯的通行归类
- **结论**：简单口语案例端到端走通，规格隔离、俗名桥接、兜底核验全部按设计工作

| real-002 微生物肥料 | 36/36/36 | 36 条 / **1.00** | 3105909000 ×3 ✓ | 3105909000 ×3 |
| real-019 淋浴房 | 39/37/39 | 35 条 / **0.81** | 7308900000 ×3（稳定但非标准答案；正确码三轮均在池） | 7308300000/7308900000/7308900000 |

候选池尾部有个位数的噪音行浮动（LLM① 用词微差导致），头部与最终结果稳定；real-019 显示终选排序仍有逐轮漂移（benchmark 各轮选中过 3 个不同编码）。残留不稳定源 = LLM 服务端，温度已为 0，代码侧已无随机源。

## 八、结论

**简化版在更少规则、更少机制的前提下全面不低于旧版**（召回 12→19 / 7→12，拒答 10→0，正确 2→5~8，单测 23/23），按预定标准**保留简化架构**，旧检索链路不再堆补丁（回滚点 `backup-before-ai-native` 保留）。

已知代价：延迟 5.5s→15s 级（3 次串行 LLM + 大候选 prompt）；终选裁定口径知识缺失成为新瓶颈（C 类 7 例）。

下一轮建议（按性价比）：
1. LLM③ 知识注入：归类总规则六条 + 本国子目注释（201 条 / 240 个税则号列）+ 归类决定摘录（切碎=已磨、预烧=陶瓷等），直击 C 类 7 例；数据管线已开工（`tools/raw/`、`tools/parse_national_notes.py`）；
2. 大品目（>12 行）展开策略：对 8703/8481/9018/3824 这类大品目允许 LLM② 请求“展开某品目更多行”的二次召回，直击 B 类 7 例；
3. 延迟优化：LLM② 与 LLM③ 的候选 prompt 裁剪（note/declareElements 截断）、理解+召回管线化。
